\section{Introduction}

The purpose of this project is to create a voice-based interface for a computer-use agent that aims to help visually impaired users operate their computer while receiving accessible feedback and retaining control. 
For the purpose of this project, a hazard is defined as any property, condition, or event that could lead to harm or loss. 
Physical harm is not expected, so harm is defined as a loss of the user's intended outcome, control, awareness, privacy, or account security. 


\section{Scope and Purpose of Hazard Analysis}

The purpose of this document is to identify and evaluate the hazards that may arise from the use of the system by considering the potential failure modes and their effects and causes, and then mitigating these risks through relevant software requirements. 
The hazards below could lead to these losses:
\begin{itemize}
  \item \textbf{Unwanted action:} Something could be sent, submitted, purchased, created, or deleted that the user did not intend. This may be costly, impossible to undo, or affect other people.
  \item \textbf{Missed or failed task:} An action that the user believes happened does not happen, or happens incorrectly.
  \item \textbf{Loss of control or awareness:} The user cannot tell what the agent is doing, cannot stop it, or is told something false.
  \item \textbf{Privacy leak:} Private information or credentials could be exposed.
  \item \textbf{Loss of independence:} If the tool slows down, stalls, or stops, the user may no longer be able to operate their computer because they may need sighted help.
\end{itemize}
These losses are amplified as a sighted user can glance at the screen to catch a mistake; a visually impaired user often cannot, so detection has to be built into the system.

\section{System Boundaries and Components}
The list below outlines the major components of the system and their roles. This is a high-level view of the system that is used to brainstorm potential hazards and is used to complete the Failure Mode and Effects Analysis (FMEA) in Section~\ref{sec:FMEA}.

\begin{enumerate}
  \item \textbf{Accessible client:} The layer that supports app functions outside voice control and task execution, such as start and stop keyboard shortcuts and viewing task history.
  \item \textbf{Voice interface:} Captures and transcribes user voice input, and provides text-to-speech audio feedback.
  \item \textbf{Task manager:} Starts, stops, and tracks tasks.
  \item \textbf{AI agent:} Plans tasks and calls tools.
  \item \textbf{Action gate:} Handles approval of consequential actions.
  \item \textbf{Outcome verification:} Verifies completed actions match what the user asked for.
  \item \textbf{Action tools and integrations:} Tools the agent uses to gather information and perform actions.
  \item \textbf{Task history layer:} Stores pending approvals, action history, task state, and any other relevant information needed to support recovery after disconnects.
\end{enumerate}
The following are outside the system boundary: the user, laptop hardware (including the microphone and speakers), the operating system (macOS), the network, AI and speech service providers, websites, and external accounts and services. Failures of these are not analyzed internally, but the system's response to them is.

\section{Critical Assumptions}

\begin{enumerate}
  \item Setup done correctly. 
    \\A setup helper completed the assisted setup (accounts connected, permissions granted), so setup errors are not analyzed as runtime hazards. Setup help may only be available weekly (for example, from an intervenor), so recovery after setup should not depend on it.
  \item One authorized speaker. 
    \\There is only one user giving commands; other voices are noise. We do not need to verify who is speaking.
  \item User's own accounts. 
    \\Connected accounts belong to the user, who may act on them. Development and evaluation use test accounts.
  \item Good faith user. 
    \\The user does not purposely misuse the system or cause harm or loss. The user also does not intentionally give misleading or vague commands; they always strive to give instructions to the best of their ability.
  \item Compatible device. 
    \\The user has a functioning laptop with a microphone and speakers running macOS with Chrome installed. Note that we will consider scenarios where the laptop has a microphone and speakers that fail mid-usage, but all laptops are assumed to have these components.
  \item Users can understand spoken output. 
    \\We assume that the user can understand the spoken output of the system. We do not analyze scenarios where the user has both vision and hearing loss. This excludes many deafblind users, such as the clients of CNIB Deafblind Community Services (from our October 17 interview \todo{link to interview?}); braille output through VoiceOver is a possible future extension.
\end{enumerate}
We do not assume that the network, speech recognition, the AI model, websites, or other external services work correctly. Their failures are analyzed in the FMEA.

\section{Safety and Security Requirements}

These requirements come from the recommended actions in Table~\ref{TblFMEA} and are also part of the SRS. FR.Sa marks functional safety requirements and NFR.Sa non-functional ones. Timing values are named constants, set after POC measurements (see the SRS constants table \todo{link to srs constant table ?}).

\subsection{Functional Safety Requirements}

\begin{itemize}
  \item \textbf{FR.Sa.1:} The system shall provide a keyboard stop control that works whenever the client is running and does not conflict with VoiceOver commands. (H1-a)
  \item \textbf{FR.Sa.2:} The system shall build the task history only from recorded actions and verified outcomes, labelling unverified entries. (H8-a)
  \item \textbf{FR.Sa.3:} Before a consequential action the system shall read back its key details. It shall proceed only after explicit approval. The cookie-rejection exception is defined in FR.Sa.13. (H2-a)
  \item \textbf{FR.Sa.4:} The system shall recognize stop requests with a fixed rule that does not depend on model interpretation. (H2-b)
  \item \textbf{FR.Sa.5:} ``Stop working'' shall pause the task and block new task actions. The system shall preserve context and distinguish acknowledgment from confirmed pause. Already-submitted operations may still finish. The system shall report completed work, unfinished work, and uncertain outcomes. Only checks of earlier outcomes may continue while paused. Work shall resume only on a clear user request. ``Cancel'' shall end the task without undoing earlier actions. (H2-c, H3-a)
  \item \textbf{FR.Sa.6:} The system shall assign each approved consequential action a unique ID and shall not repeat an action with the same ID. (H3-b)
  \item \textbf{FR.Sa.7:} The system shall pause the task while the user is disconnected. (H3-b)
  \item \textbf{FR.Sa.8:} Task state and approval records shall survive restart. The system shall announce interrupted tasks with their last known state. Unused approvals shall be withdrawn. (H8-b)
  \item \textbf{FR.Sa.9:} The system shall ask a clarifying question when details required for an action are missing or ambiguous. (H4-a)
  \item \textbf{FR.Sa.10:} Completion claims shall use evidence matching the intended action and details. Evidence may be a meaningful connector result, account record, or website confirmation. Unclear evidence requires another check or an unknown result. Report verified, partial, failed, and unknown outcomes separately. Queuing shall not be reported as delivery. (H4-b, H6-a, H6-b, H7-a)
  \item \textbf{FR.Sa.11:} A configured step or time limit shall pause the task and prompt the user. A task step shall mean one attempted agent-directed tool operation, including failed attempts; internal reasoning and time spent waiting for the user shall not count as steps. The step count shall persist across pause and resumption of the same task and reset for a new task. Time spent waiting for user clarification or approval shall not count toward the execution time limit. (H4-c)
  \item \textbf{FR.Sa.12:} If a read-only lookup fails due to a temporary service error, the system may retry it once. If the retry fails, or if an external service failure affects any other operation, the system shall pause work and report completed, unfinished, and uncertain outcomes. Consequential actions shall not be automatically retried. (H4-d)
  \item \textbf{FR.Sa.13:} Writes and consequential commitments shall require approval. These include submissions, external messages, saved data changes, and granting access. Navigation and temporary preparation may proceed if they have no such effect. Unclear effects require approval. The system may automatically choose a clearly identified ``reject non-essential cookies'' or ``necessary only'' option. Any ambiguous consent choice shall require explicit user approval. (H5-a)
  \item \textbf{FR.Sa.14:} The system shall bind each approval to the action's exact details, use it once, and require new approval if any detail changes. (H5-b, H7-a)
  \item \textbf{FR.Sa.15:} When pending approval is withdrawn the system shall say the pending action was not executed. It shall distinguish earlier completed work. (H5-c)
  \item \textbf{FR.Sa.16:} The system shall treat webpage and email content as data, and shall only perform consequential actions that trace to the user's request. (H7-b)
  \item \textbf{FR.Sa.17:} The system shall request only the account permissions needed for each integration. Stored credentials and website passwords shall be entered through private input, stored securely, and excluded from AI model context, application history, logs, and source control. One-time authentication codes may be spoken by the user; the system shall disclose that spoken codes may be processed by its speech and conversation providers. (H7-c)
  \item \textbf{FR.Sa.18:} The system shall check the service or item state directly and confirm the user's approval before retrying an action whose outcome is unknown. (H7-d)
  \item \textbf{FR.Sa.19:} Before deletion the system shall read back identifying details. It shall explain whether the operation can be undone. It shall prefer recoverable deletion where supported. (H5-d)
  \item \textbf{FR.Sa.20:} If voice input, voice output, or speech services become unavailable, the system shall pause the task and block new task actions when the failure is detected. The system shall preserve task state and record the outcomes of previously submitted operations. Work shall resume only after voice communication is restored and the user explicitly requests resumption. (H2-c)
\end{itemize}
\subsection{Non-Functional Safety Requirements}

\begin{itemize}
  \item \textbf{NFR.Sa.1:} The system shall audibly acknowledge a stop request within STOP\_ACK\_TIME of the end of the utterance or key press. (H2-b)
  \item \textbf{NFR.Sa.2:} The system shall notify the user of a lost connection within CONNECTION\_NOTICE\_TIME, by sound if speech is unavailable. (H3-b)
  \item \textbf{NFR.Sa.3:} While the system is actively working on a task, including planning, browsing, searching, read-only lookups, and executing actions, it shall provide a spoken progress update or report a blocker before IDLE\_PROMPT\_TIME elapses without spoken progress. Time spent awaiting user clarification or approval, or while the task is paused or cancelled, shall not count toward this interval. (H4-c)
\end{itemize}
