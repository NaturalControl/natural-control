\chapter*{Glossary}
\addcontentsline{toc}{chapter}{Glossary}

Project terms:

\begin{itemize}
    \item User: the person who owns the connected accounts and gives commands. Other voices in the room are not users.
    \item Setup helper: a person who completes the initial assisted setup for the user.
    \item Session: the period during which the user is talking with the system, started and ended with the client's start control or a keyboard shortcut, or ended by disconnection. A session can contain several tasks.
    \item Task: one job the user asks for. It may pause before it is completed, cancelled, or failed.
    \item Consequential action: a write to user or account data, a submission, an external message, or a commitment such as accepting terms or granting access. Navigation and temporary preparation do not need approval unless they cause one of these effects. \reqlink{FR24} defines one exception for rejecting non-essential cookies.
    \item Approval: the user's explicit consent to one consequential action, or to a listed batch of similar actions, with their specific details; used once and void if any detail changes.
    \item Barge-in: the user speaking while the system is speaking; it stops the speech only.
    \item Stop request: an explicit ``stop working'' command or stop key. It pauses work and preserves the task. Cancellation ends the task.
    \item Pause acknowledged: the system received the stop request. Pause confirmed: no new task actions can start. Any earlier operation that is still pending is reported separately.
    \item Verified outcome: a result supported by a matching tool response, account record, or website confirmation. Unknown outcome: an action whose result cannot be determined.
\end{itemize}

\nsection{G.1 Context and overall objective}

Many websites and applications communicate information, choices, and state changes visually. Blind users can face barriers completing multi-step digital tasks and knowing whether those tasks succeeded. 
Natural Control is a voice interface that lets a blind user delegate tasks in a web browser and in connected apps to an AI agent, while staying informed and in control. 

\nsection{G.2 Current situation}

Today, blind users complete these tasks with screen readers such as VoiceOver, navigating each interface element by element, or with help from a sighted person. Existing AI computer-use agents assume the user can watch the screen to monitor and correct them.

In an interview with a former CNIB Deafblind Community Services (DBCS) staff member on October 17, 2026 (\hyperref[app:interview]{transcript in the appendix}), the participant observed that screen readers are hard to learn for older, newly diagnosed users and often read irrelevant content, and that everyday tasks such as booking appointments often need a friend's help.

\nsection{G.3 Expected benefits}

\begin{itemize}
    \item Delegate, don't navigate: the user simply states an outcome (``reply to Alex'') instead of visually navigating the interface step by step. (\reqlink{G1})
    \item Control without sight: the user can understand, approve, correct, and stop the agent without seeing the screen. (\reqlink{G2}, \reqlink{G4})
    \item Trustworthy results: results are checked against the real account or page before being reported, so the user does not need sighted help to confirm what happened. (\reqlink{G3}) Correcting a wrong result after the fact is slow and costly for blind users \citep{AzenkotLee2013}.
\end{itemize}

\nsection{G.4 Functionality overview}

\begin{itemize}
    \item \textbf{Delegated task execution:} carries out multi-step tasks in a web browser or a connected app from a single spoken goal, instead of the user navigating each step.
    \item \textbf{Clarification on demand:} asks for clarification when required details are missing or ambiguous rather than guessing about the user's intent.
    \item \textbf{Approval-gated actions:} requires explicit approval of exact details before completing consequential actions, such as sending, saving, or submitting.
    \item \textbf{Verified reporting:} checks task outcomes against the real account or page before reporting them as complete, rather than assuming a success after actions are taken.
    \item \textbf{Mid-task control:} accepts corrections, stop requests, barge-ins, and cancellation at any point during a task.
    \item \textbf{Accessible task history:} records what happens and makes the system's history reviewable by voice or through the keyboard and VoiceOver.
\end{itemize}

\nsection{G.5 High-level usage scenarios}

\begin{itemize}
    \item \textbf{Scenario 1: Reply to an email.} A user asks the system to find a specific email and reply with a short message, approving the exact reply before it sends.
    \item \textbf{Scenario 2: Add a webpage event to Google Calendar.} A user asks the system to read an event off a webpage and add it to their calendar, hearing the details read back before it is created.
    \item \textbf{Scenario 3: Compare information on an unfamiliar website.} A sighted user who wants nonvisual interaction asks the system to compare different sets of prices for something on an unfamiliar website.
    \item \textbf{Scenario 4: Correct or stop a running task.} A user interrupts an in-progress task with a correction or an explicit stop request, and the system reports what has and has not completed.
    \item \textbf{Scenario 5: Reconnect after a dropped connection.} A user reconnects after losing their connection mid-task and resumes only after hearing the current state, without duplicating any action.
\end{itemize}

\nsection{G.6 Limitations and exclusions}

\begin{itemize}
    \item Native Mac application control and general local-file tasks.
    \item Platforms other than Mac with Chrome; languages other than English.
    \item Phone calling and saved workflows (stretch goals).
    \item Background continuation: tasks always pause when the user disconnects; continuing unattended is a possible extension.
    \item Fully local model inference; the system uses cloud AI and speech providers.
    \item Users who cannot hear spoken output, including many deafblind users. Braille output through VoiceOver is a possible extension.
\end{itemize}

\nsection{G.7 Stakeholders and requirements sources}

\begin{itemize}
    \item Primary: blind and visually impaired people who want to complete digital tasks without visual feedback. Initial evaluation: blind Mac users with screen-reader experience.
    \item Secondary: other people who want nonvisual interaction.
    \item Tertiary: website and application developers who affect the system's operational limits.
    \item Setup helper: a person who completes the assisted setup.
    \item Intervenors: support workers who may help deafblind users with setup and recovery.
    \item Requirements sources: the Problem Statement, Development Plan, and Hazard Analysis documents; TA and instructor guidance; prior research (WebAIM survey \citep{WebAIM2024}, Morae \citep{Morae2025}, Azenkot and Lee \citep{AzenkotLee2013}); an interview with a former CNIB Deafblind Community Services (DBCS) staff member on October 17, 2026 (\hyperref[app:interview]{transcript in the appendix}); and planned participant sessions.
\end{itemize}

\nsection{G.8 User profiles}

The following is an expansion of the stakeholder groups who will actually use and benefit from our system. They are designed to demonstrate specific examples of
who may be interacting with our system, and are intended to be refined after proper recruitment of participants has been completed.

\begin{itemize}
    \item Experienced screen-reader user: fluent with VoiceOver or JAWS and keyboard navigation; wants speed on multi-step tasks and keeps their screen reader for everything else. Primary evaluation group.
    \item Less experienced or recently blind user: often older, with acquired vision loss, limited screen-reader skill, and possibly an older device; benefits most from delegation and clear spoken confirmation.
    \item Sighted user wanting nonvisual interaction: can see the screen but prefers or needs voice (busy hands, away from the screen); can verify visually, so has lower risk.
    \item Setup helper: comfortable with computers; connects accounts and grants permissions once, then is not needed for daily use.
\end{itemize}

\nsection{G.9 Goals}

The goals below are copied from Section 2 of the Problem Statement document. Their identifiers (G1 to G5) are the trace targets used in the requirement tables of S.2, and are distinct from the section numbers of this book (G.1 to G.9).

\begin{description}
    \item[\reqtarget{G1}.] \textbf{Complete complex digital tasks independently.}
    Within the initial browser and connected-account scope, users should be able to
    complete common, multi-step tasks without
    relying on visual feedback or sighted assistance. Success can be measured by task completion rate
    and the amount of sighted assistance that is required.

    \item[\reqtarget{G2}.] \textbf{Maintain awareness and control during digital tasks.}
    Users should be able to understand relevant task progress and state changes, provide input when required,
    and stop or redirect tasks when necessary. Measure successful corrections, explicit stop acknowledgment and execution-stop
    confirmation, and approval before consequential actions. Clarification counts
    provide context; fewer questions alone do not establish better control.

    \item[\reqtarget{G3}.] \textbf{Accurately receive results and execute commands.}
    Users should be able to have confidence that the program is correctly tracking the system's state,
    retrieving results, and executing their desired actions and commands. Compare reported outcomes and executed actions against independently verified
    application state and the user's request. Report incorrect or unsupported
    completion claims separately from successful actions.

    \item[\reqtarget{G4}.] \textbf{Recover from errors and unexpected outcomes.}
    Users should be able to identify unexpected, misunderstood, or failed actions and recover without restarting
    the entire task or relying on sighted assistance. Measure whether recovery succeeds without sighted help or a full restart,
    along with recovery time and clarification turns.

    \item[\reqtarget{G5}.] \textbf{Provide a straightforward and reliable setup process.}
    Individuals responsible for setting up the interface should have a smooth setup process.
    Routine use after initial setup should not require assistance from the setup helper. Success can be measured by the number of clicks or commands needed,
    the setup time before the program can be used, as well as how many times the setup helper is required to assist after installation.
\end{description}

\nsection{E.2 Components}

This section contains a list of elements of the environment that may affect or be affected by the system, including other systems
the system must interface with.

\begin{itemize}
    \item Users: the person giving spoken commands and acting on the system's results; see the Glossary and G.7--G.8 for roles and profiles.
    \item Laptop hardware: the user's Mac, including its microphone and speakers.
    \item Platform: macOS with Google Chrome, and the user's existing VoiceOver screen reader.
    \item Network: required for cloud speech, AI, and connected apps' API traffic.
    \item AI model and speech providers: cloud services for language understanding, speech-to-text, and text-to-speech.
    \item Websites the user asks about (unmodified, not under our control).
    \item External accounts and services.
    \item Composio cloud: an external hosted service that stores OAuth tokens for our connected apps. Its ``Don't store data'' setting is turned on so tool inputs and outputs are not logged. Our own code calls it through the Composio SDK (S.1).
\end{itemize}

\nsection{E.3 Constraints}

The following is a list of obligations and limits imposed by the environment.

\begin{itemize}
    \item Mac with Google Chrome, in English.
    \item Provider terms of use and data retention policies apply to anything sent to them.
    \item A hosted backend cannot reach the user's Mac or its signed-in browser sessions, so controlling the user's own browser requires a component running locally.
\end{itemize}

\nsection{E.4 Assumptions}

\begin{itemize}
    \item A setup helper completed setup correctly (accounts connected, permissions granted).
    \item Only the user gives commands; other voices are noise.
    \item Connected accounts belong to the user; development and evaluation use test accounts.
    \item The user can hear spoken output (see G.6).
\end{itemize}

Speech recognition, the AI model, websites, and external services are not assumed to work correctly; their failures are covered by the Hazard Analysis and S.5.

\nsection{E.5 Effects}

\begin{itemize}
    \item Users will rely less on outside help to complete computer tasks, as the system will assist in their completion.
    \item Desired properties in connected apps are affected (e.g. read, created, updated, or deleted).
    \item Website forms may be filled and submitted by the system, subject to user approval.
    \item Input data can reach AI and speech vendors.
    \item Content and progress is processed and reported back to the user through the computer's speaker hardware.
\end{itemize}

\nsection{E.6 Invariants}

\begin{itemize}
    \item External account and page states can change outside the system at any time, through other devices, other users, or the provider itself; the system's last known state should not be assumed current.
    \item A delivered message or submitted form cannot be withdrawn by the system after the fact; only the provider or recipient can undo it, if at all.
    \item Authentication codes (and credentials from services like OAuth) are controlled by the provider: they expire, can be revoked, and may require re-authorization independent of the system's own state.
    \item The user's existing accessibility tools (VoiceOver, keyboard navigation) keep working while the system runs.
\end{itemize}

\nsection{E.7 Standards and legal/regulatory factors}

\begin{itemize}
    \item WCAG 2.2 Level AA: accessibility standard for the web client, adopted voluntarily \citep{WCAG22}.
    \item AODA (Accessibility for Ontarians with Disabilities Act): Ontario accessibility law referencing WCAG; its compliance obligations are not required as they apply to organizations with Ontario employees (20+ for reporting, 50+ for website compliance), but it is a relevant reference for our team \citep{AODAFactSheet}.
    \item Open-source licenses: our code uses MIT licensing; reused components keep their own licenses and notices.
    \item Coding standards: PEP 8 for Python; strict TypeScript with a shared linter for the client.
\end{itemize}

\nsection{S.1 Components}

The proposed system has eight components. These match the Hazard Analysis. Figure~\ref{fig:components} shows their connections and external services. Team-owned components are planned work. The POC must test the integration boundaries.



\begin{itemize}
    \item \textbf{Accessible client:} the web interface for sessions and task history. It provides keyboard controls and works alongside VoiceOver.
    \item \textbf{Voice interface:} uses LiveKit for audio and conversational turn handling. Our integration passes requests and corrections to the task manager. It speaks relevant questions and results.
    \item \textbf{Task manager:} starts tasks and tracks their state. It handles corrections, pauses, cancellation, and resumption (S.9).
    \item \textbf{AI agent:} Hermes plans tasks and proposes tool calls. Each call must pass through the action gate.
    \item \textbf{Action gate:} checks every proposed action. It requests approval for writes and consequential commitments. Approval details come from the proposed call. The gate also blocks new task actions while work is paused.
    \item \textbf{Outcome verification:} checks evidence for each consequential action. Evidence may come from its tool response or a targeted account or page check. The result is recorded as verified, partial, failed, or unknown.
    \item \textbf{Action tools and integrations:} Browser Use handles websites. Connected app tools use the Composio SDK. The proposed integration places approval checks before execution and outcome checks afterward. The POC must verify that all action paths pass through these checks. Credential handling also needs verification.
    \item \textbf{Task history layer:} records task state and action outcomes. It also records approvals and action IDs. These records support accessible review and recovery after disconnection.
\end{itemize}

\subsection*{S.2.7 Safety requirements}
\addcontentsline{toc}{subsection}{S.2.7 Safety requirements}

The following safety requirements are based on the Hazard Analysis. Hazard IDs refer to its FMEA rows.

\paragraph{Functional safety requirements}
\begin{itemize}
  \item \textbf{\reqtarget{FR.Sa.1}:} The system shall provide a keyboard stop control that works whenever the client is running and does not conflict with VoiceOver commands. (H1-a)
  \item \textbf{\reqtarget{FR.Sa.2}:} The system shall build the task history only from recorded actions and verified outcomes, labelling unknown entries. (H8-a)
  \item \textbf{\reqtarget{FR.Sa.3}:} Before a consequential action the system shall read back its key details. It shall proceed only after explicit approval. The cookie-rejection exception is defined in FR.Sa.13. (H2-a)
  \item \textbf{\reqtarget{FR.Sa.4}:} Explicit stop phrases and the stop key shall use a fixed control path. They shall not depend on the planning agent choosing to pause. (H2-b)
  \item \textbf{\reqtarget{FR.Sa.5.i}:} After a stop-work request, the system shall pause the task and block all further actions for it. Only checks of earlier outcomes may continue running. (H2-c, H3-a)
  \item \textbf{\reqtarget{FR.Sa.5.ii}:} After a stop-work request, the system shall immediately acknowledge and confirm completion of the request as separate messages before reporting completed work, unfinished work, and uncertain outcomes. (H3-a)
  \item \textbf{\reqtarget{FR.Sa.5.iii}:} When a task is paused, an explicit user request shall resume or terminate the task. If terminated, earlier actions are not undone. (H3-a)
  \item \textbf{\reqtarget{FR.Sa.6}:} Each approved action shall have a unique ID. An action with that ID shall not execute twice. (H3-b)
  \item \textbf{\reqtarget{FR.Sa.7}:} Disconnection shall block new task actions and pause the task. Reconnection alone shall not resume it. (H3-b)
  \item \textbf{\reqtarget{FR.Sa.8}:} Task state and approval records shall survive restart. The system shall announce interrupted tasks with their last known state. Unused approvals shall be withdrawn. (H8-b)
  \item \textbf{\reqtarget{FR.Sa.9}:} The system shall ask a clarifying question when details required for an action are missing or ambiguous. (H4-a) 
  \item \textbf{\reqtarget{FR.Sa.10}:} The system shall report a task as verified, failed, or partial only after verifying its outcome with evidence that matches the intended action and its details, such as a connector result, an account record, or a website confirmation. If the evidence is unclear, the system shall check again or report the outcome as unknown. (H4-b, H6-a, H6-b, H7-a)
  \item \textbf{\reqtarget{FR.Sa.11}:} A configured step or time limit shall pause the task and prompt the user. Time spent waiting for user clarification or approval shall not count toward the execution time limit. (H4-c)
  \item \textbf{\reqtarget{FR.Sa.12}:} An external service failure shall pause work and the system shall follow the steps outlined in \reqlink{FR.Sa.5.i}, \reqlink{FR.Sa.5.ii}, and \reqlink{FR.Sa.5.iii}. (H4-d)
  \item \textbf{\reqtarget{FR.Sa.13}:} Unclear actions and consequential actions such as submissions, external messages, saved data changes, or granting permission require explicit approval before being executed; only actions with no such lasting effect do not require approval. One exception to this rule: rejecting non-essential cookies or only allowing necessary cookies on webpages does not require explicit approval. (H5-a)
  \item \textbf{\reqtarget{FR.Sa.14}:} The system shall bind each approval to the action's exact details, use it at most once, and require new approval if any detail changes. A pause, disconnection, cancellation, or task replacement shall withdraw unused approvals. (H5-b, H7-a)
  \item \textbf{\reqtarget{FR.Sa.15}:} When a pending approval expires or is withdrawn, the system shall tell the user that the action was not executed and shall state which earlier actions were completed. (H5-c)
  \item \textbf{\reqtarget{FR.Sa.16}:} The system shall treat webpage and email content as data, and shall only perform consequential actions that trace to the user's request. (H7-b)
  \item \textbf{\reqtarget{FR.Sa.17}:} The system shall request only the account permissions each tool needs, and shall store and use passwords and other credentials securely, keeping them out of source control, logs, and the AI model input. (H7-c)
  \item \textbf{\reqtarget{FR.Sa.18}:} The system shall check the service or item state directly and confirm the user's approval before retrying an action whose outcome is unknown. (H7-d)
  \item \textbf{\reqtarget{FR.Sa.19}:} Before deletions, the system shall read back the item's identifying details, state whether the operation is reversible, and use recoverable deletion where supported. (H5-d)
  \item \textbf{\reqtarget{FR.Sa.20}:} If voice input, voice output, or speech services become unavailable, the system shall stop as outlined in \reqlink{FR.Sa.5.i}, accept no new tasks requests until voice functionality is restored, and shall not resume unless user explicitly requests it. (H2-c)
\end{itemize}

\paragraph{Non-functional safety requirements}
\begin{itemize}
  \item \textbf{\reqtarget{NFR.Sa.1}:} The system shall audibly acknowledge a stop request within STOP\_ACK\_TIME of the end of the utterance or key press. (H2-b)
  \item \textbf{\reqtarget{NFR.Sa.2}:} The client shall signal disconnection within CONNECTION\_NOTICE\_TIME. A local sound shall be used if network speech is unavailable. (H3-b)
  \item \textbf{\reqtarget{NFR.Sa.3}:} While a task is running, the system shall give a spoken status update after IDLE\_PROMPT\_TIME without spoken progress, outlining progress made or blockers. (H4-c)
\end{itemize}

\nsection{S.3 Interfaces}

\begin{itemize}

Approval details and history are accessible through VoiceOver and the keyboard. Spoken questions can be repeated on request. The system shall explain the keyboard shortcut for stopping work during setup and repeat the shortcut on request. The shortcut shall not conflict with VoiceOver controls.
    \item \textbf{Program interfaces:} LiveKit carries audio and speech events. The Hermes integration carries task requests, corrections, and progress. The task manager controls execution separately from speech. Browser Use and Composio supply action tools. Each tool call passes through the gate.

\Needspace{8\baselineskip}
\nsection{S.4 Normal operation}

Figure~\ref{fig:seqnormal} follows one request from start to finish: the user asks to add an event found on a webpage to their calendar.

\begin{enumerate}
    \item The user starts a session from the client (\reqlink{FR22}) and speaks the request. The voice interface passes it to the task manager. It records the task and starts the agent in Working. The user hears a short acknowledgment.
    \item The agent reads the page. The action gate lets this read-only call through to Browser Use and screens the returned content for injected instructions (\reqlink{FR10}, \reqlink{FR13}).
    \item The agent proposes event creation. The gate holds the write and requests approval of its exact details. The task enters AwaitingApproval.
    \item The voice interface reads the details back. The user says ``yes.'' The task manager records approval and releases the call. The task enters Executing (\reqlink{FR9}).
    \item The gate submits the call with a unique action ID (\reqlink{FR11}). The returned event details confirm creation. Outcome verification checks those details and reports the result (\reqlink{FR12}). A separate lookup is used if the response is unclear.
    \item The agent finishes the task (state Done). The task history records each step (\reqlink{FR15}), and the user hears the verified result.
\end{enumerate}

\nsection{S.5 Undesired event handling}

\begin{itemize}
    \item \textbf{Misheard or ambiguous request:} ask for clarification. Read back key details before approval. (H2-a, H4-a)
    \item \textbf{Missed work-stop request:} provide a keyboard backup. Block new task actions once the request is recognized. (H2-b, H3-a)
    \item \textbf{Disconnection:} pause work. Report the state after reconnection and wait for an instruction to resume. (H3-b)
    \item \textbf{Provider failure:} pause work. Explain what completed and what remains unfinished or unknown. (H4-d)
    \item \textbf{Unknown outcome:} check the affected account or page before any retry. Ask the user if the outcome remains unknown. (H7-d)
    \item \textbf{Injected instructions:} treat webpage and email text as data. Do not let it authorize actions. (H7-b)
\end{itemize}

\nsection{S.6 Detailed usage scenarios}

The five use cases below expand the high-level scenarios in G.5. Each lists the main success scenario and its extensions. Extensions are numbered by the step they branch from: ``2a'' branches from step 2.

\Needspace{12\baselineskip}
\subsection*{UC1: Reply to an email}
\addcontentsline{toc}{subsection}{UC1: Reply to an email}

\textbf{Primary actor:} User

\textbf{Preconditions:} A session is active, Gmail is connected through the account tools, and no other task is active.

\textbf{Trigger:} ``Reply to Alex Chen's invitation and say Friday at 2 works for me.''

\textbf{Main success scenario:}
\begin{enumerate}
    \item The voice interface passes the request to the task manager. It starts the task.
    \item The agent searches the inbox (read-only) and finds the invitation.
    \item The agent prepares the reply without saving a draft. The gate holds the send and requests approval.
    \item The system reads back the recipient, subject, and full body: ``Send to Alex Chen, subject Re: Invitation: Thanks for the invitation, Friday at 2 works for me. Send it?''
    \item The user says ``Yes, send it.''
    \item The gate sends the reply with a unique action ID. Outcome verification finds the matching message in Sent.
    \item The user hears ``Your reply was sent to Alex Chen.'' The task history records the request, approval, action, and outcome.
\end{enumerate}

\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} Two possible contacts match. The system asks which one (\reqlink{FR4}). It waits for the answer and repeats the question on request (\reqlink{FR5}).
    \item \textbf{4a.} The body exceeds SHORT\_MESSAGE\_LENGTH. The system reads the recipient and subject. It summarizes the body and offers a full read-back (\reqlink{FR9}).
    \item \textbf{4b.} The user says ``change Friday to Monday.'' That detail changes and is read back. Earlier approval no longer applies (\reqlink{FR16}, \reqlink{FR9}).
    \item \textbf{5a.} The user declines or requests another task. Approval is withdrawn. The user hears that this reply was not sent (\reqlink{FR20}).
    \item \textbf{6a.} The send cannot be confirmed. The system reports failure only with evidence of failure. Otherwise it reports unknown (\reqlink{FR12}).
\end{itemize}

\textbf{Success guarantee:} Only the approved reply is sent to the intended recipient. The reported result matches the sending evidence. Delivery or reading by the recipient is not claimed.

\textbf{Failure guarantee:} Nothing is sent without approval of its exact recipient and text. The user hears whether sending was confirmed or remains uncertain.

\Needspace{12\baselineskip}
\subsection*{UC2: Add an event from a webpage to the calendar}
\addcontentsline{toc}{subsection}{UC2: Add an event from a webpage to the calendar}

\textbf{Primary actor:} User

\textbf{Preconditions:} A session is active, Google Calendar is connected, and the page is public or has a saved login (\reqlink{FR23}).

\textbf{Trigger:} ``Add the meetup on this page to my calendar.''

\textbf{Main success scenario:}
\begin{enumerate}
    \item The task manager starts the task. The user hears a short acknowledgment.
    \item The browser opens the page. A clear non-essential cookie prompt is rejected under \reqlink{FR24}.
    \item The agent reads the event title, date, time, and place (read-only).
    \item The agent proposes event creation. The gate holds it. The system reads back the details.
    \item The user approves.
    \item The gate creates the event with a unique action ID. Outcome verification checks the returned details or a matching calendar record.
    \item The user hears the verified result (Figure~\ref{fig:seqnormal}).
\end{enumerate}

\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} The consent prompt is unclear. The system asks the user before choosing an option (\reqlink{FR24}).
    \item \textbf{3a.} The page tells the agent to ignore the user or send information elsewhere. The system treats this text as data. It does not follow those instructions (\reqlink{FR13}).
    \item \textbf{3b.} The end time is missing. The system asks instead of guessing (\reqlink{FR4}).
    \item \textbf{3c.} A matching event already exists. The system reports it before asking for approval.
    \item \textbf{5a.} The user declines. No event is created. The system reports this.
\end{itemize}

\textbf{Success guarantee:} The calendar contains one approved event. A matching creation response or calendar record confirms its details.

\textbf{Failure guarantee:} No event is created without approval. Uncertain creation is reported as unknown.

\Needspace{12\baselineskip}
\subsection*{UC3: Compare information on a website}
\addcontentsline{toc}{subsection}{UC3: Compare information on a website}

\textbf{Primary actor:} User

\textbf{Preconditions:} A session is active. The site is public, or its login was saved through the vault page (\reqlink{FR23}).

\textbf{Trigger:} ``On this conference site, compare the standard and student tickets.''

\textbf{Main success scenario:}
\begin{enumerate}
    \item The task manager starts the task.
    \item The agent navigates without making a consequential change. Clear non-essential cookie prompts follow \reqlink{FR24}.
    \item The agent gathers each ticket's price and what it includes.
    \item The user hears a short comparison limited to the request. Uncertain details are stated. For example, fees may be unclear (\reqlink{FR18}, \reqlink{FR12}).
    \item The user corrects the request: ``Only compare tickets that include workshops.''
    \item The agent rechecks and reports the corrected comparison (\reqlink{FR6}). Nothing is purchased or submitted.
\end{enumerate}

\textbf{Extensions:}
\begin{itemize}
    \item \textbf{2a.} A saved login exists. The agent uses it only on its intended site (\reqlink{FR23}).
    \item \textbf{2b.} No login is saved. The system explains the private setup route. The task pauses for setup.
    \item \textbf{2c.} The site requests a one-time code or push approval. The user may speak the code or approve on their device (\reqlink{FR23}).
    \item \textbf{2d.} The site requires a device-bound passkey. The system explains the manual handoff when that requirement becomes known.
    \item \textbf{5a.} The user asks to buy a ticket. This requires approval of the purchase details. It follows the approval and verification flow in UC1.
\end{itemize}

\textbf{Success guarantee:} The comparison matches the site and the corrected request. Unconfirmed details are stated.

\textbf{Failure guarantee:} No purchase or submission bypasses approval. Authentication follows \reqlink{FR23}.

\Needspace{12\baselineskip}
\subsection*{UC4: Correct or pause a running task}
\addcontentsline{toc}{subsection}{UC4: Correct or pause a running task}

\textbf{Primary actor:} User

\textbf{Preconditions:} A task is active.

\textbf{Trigger:} The user says ``stop working'' or presses the stop key.

\textbf{Main success scenario:}
\begin{enumerate}
    \item The user requests a pause while an approved event creation is in progress.
    \item The voice interface recognizes the stop phrase and says ``Pausing work'' within STOP\_ACK\_TIME (\reqlink{FR3}, \reqlink{NFR3}).
    \item The task manager enters Pausing. The gate blocks new task actions. Unused approvals are withdrawn. Safely cancellable work is interrupted.
    \item The submitted event creation cannot be cancelled safely. It returns a matching event record. The system records that result (\reqlink{FR8}, \reqlink{FR12}).
    \item The task enters Paused. The user hears ``Paused. The event was already added. The remaining work has not run.''
    \item The user may ask questions while work stays paused. A clear request to continue resumes the task after state checks. Any remaining writes need fresh approval.
\end{enumerate}

\textbf{Extensions:}
\begin{itemize}
    \item \textbf{1a.} The user corrects the task instead. The agent receives the correction (\reqlink{FR6}). Changed action details require fresh approval (\reqlink{FR9}).
    \item \textbf{1b.} The user says only ``stop.'' Speech stops and work pauses. The system asks what the user wants next (\reqlink{FR3}).
    \item \textbf{4a.} A form was prepared but not submitted. Its context is saved where possible. The system says it was not submitted. Resumption requires a check that the page still matches the request.
    \item \textbf{4b.} The earlier submission times out. The task remains paused. The system reports its outcome as unknown. Reconciliation may continue without advancing the task. It does not retry blindly (\reqlink{FR11}).
    \item \textbf{6a.} The user cancels. The task enters Cancelling and then Cancelled. Earlier actions are reported and are not undone automatically.
\end{itemize}

\textbf{Success guarantee:} No new task action starts after the recognized stop request until the user resumes. Checks may only reconcile earlier actions. The user hears what completed and what remains.

\textbf{Failure guarantee:} An uncertain external result stays labelled unknown. A confirmed pause is not presented as cancellation of an earlier submission.

\Needspace{12\baselineskip}
\subsection*{UC5: Reconnect without duplicating an action}
\addcontentsline{toc}{subsection}{UC5: Reconnect without duplicating an action}

\textbf{Primary actor:} User

\textbf{Preconditions:} A task is active and the connection drops.

\textbf{Trigger:} The connection to the user is lost.

\textbf{Main success scenario:}
\begin{enumerate}
    \item The task pauses (\reqlink{FR7}). The client signals connection loss within CONNECTION\_NOTICE\_TIME. A local sound is used if network speech is unavailable (\reqlink{NFR.Sa.2}).
    \item The user reconnects, or starts a new session later.
    \item The system briefly reports the task's state: what completed, what was pending, and anything uncertain (\reqlink{FR18}, \reqlink{FR21}).
    \item The user says ``continue.'' The system checks relevant state before resuming. Any unused approval is requested again.
\end{enumerate}

\textbf{Extensions:}
\begin{itemize}
    \item \textbf{1a.} Approval was pending. It is withdrawn. On reconnection the user hears that the pending action was not executed. Resumption needs fresh approval (\reqlink{FR20}).
    \item \textbf{1b.} An action was already submitted. Its outcome is checked before a retry. The same action ID never executes twice (\reqlink{FR11}).
    \item \textbf{4a.} The user cancels instead of continuing. The task ends after cancellation handling. The user hears what had already completed.
\end{itemize}

\textbf{Success guarantee:} No completed action is repeated as a retry. The user hears the task state before it continues.

\textbf{Failure guarantee:} Uncertain state is reported. Work does not resume silently.

\Needspace{8\baselineskip}
\nsection{S.9 Formalization: task state machine}

Each task has one state $q \in Q$, where
$Q = \{$Working, AwaitingClarification, AwaitingApproval, Executing, Pausing, Paused, Cancelling, Cancelled, Done, Failed$\}$.
The partial transition function $\delta : Q \times \Sigma \to Q$ uses the events in Table~\ref{tab:fsm}. Figure~\ref{fig:states} summarizes task control.

The running states are Working, AwaitingClarification, AwaitingApproval, and Executing. Pausing, Paused, and Cancelling are also active states. Cancelled, Done, and Failed are final. A session has at most one active task.

The maximum silence timer in \reqlink{NFR.Sa.3} counts active work in both Working and Executing, including read-only work; it excludes time awaiting user clarification or approval and time paused or cancelled.

A work-stop request blocks new task actions as soon as it is recognized. Pausing records this change and requests safe interruption. It then enters Paused. An earlier external operation may still be pending. Its outcome is tracked separately. Reconciliation checks may continue while paused. They may not advance the task. The report distinguishes unfinished work from unknown outcomes.

Cancellation uses Cancelling to block new actions and preserve earlier results. It then enters Cancelled. Earlier operations are not undone. An unresolved external submission does not justify repeating it.

Pending approvals are withdrawn on pause, disconnection, or cancellation. They do not expire merely because a connected user takes time to answer. Resumption requires a clear instruction and a check of relevant state. Unused writes need fresh approval. A new voice session alone does not resume work. New requests follow \reqlink{FR19}.

Required properties:

\nsection{P.6 Risk and mitigation analysis}

\begin{itemize}
    \item Risk: Supervision through Hermes may not work as documented.
    \begin{itemize}
        \item Description: Hermes's documented approval, interrupt, and reconnection behavior may not match its actual behavior once integrated.
        \item Mitigation: Test approvals, interrupts, and reconnection on a pinned version first; revisit the adapter/harness before promising supervision if unavailable.
    \end{itemize}
    \item Risk: Browser actions may not be interceptable for approval.
    \begin{itemize}
        \item Description: Browser Use may not expose a reliable point to pause and request approval before a consequential action executes.
        \item Mitigation: If interception is not possible, the browser becomes read-only for the initial release.
    \end{itemize}
    \item Risk: Recruitment of blind participants may fail.
    \begin{itemize}
        \item Description: The team aims to recruit two to four blind participants with screen-reader experience; recruitment is not yet complete.
        \item Mitigation: Report technical feasibility only and disclose missing usability evidence.
    \end{itemize}
    \item Risk: Provider costs may exceed the budget.
    \begin{itemize}
        \item Description: Cloud AI, speech, and hosting costs scale with usage and are not fully known in advance.
        \item Mitigation: Monitor usage and reconcile monthly.
    \end{itemize}
    \item Risk: Tasks may take longer than expected, or workload may become unbalanced across the team.
    \begin{itemize}
        \item Description: Our four members aim to cover distinct workstreams (voice/client, agent/tools, deployment/reliability, evaluation/quality) during development; scheduling difficulties in one area can cascade into others.
        \item Mitigation: Use the GitHub Kanban board to track tasks and milestones; check-in and redistribute blocked work at the weekly sync.

\end{itemize}
