\chapter*{Glossary}
\addcontentsline{toc}{chapter}{Glossary}

Project terms (from GLOSSARY.md):

\begin{itemize}
    \item User: the person who owns the connected accounts and gives commands. Other voices in the room are not users.
    \item Setup helper: a person who completes the initial assisted setup for the user.
    \item Session: the period during which the user is talking with the system, started from the client's start control and ended by the user or by disconnection. A session can contain several tasks.
    \item Task: one job the user asks for, from request until it is done, failed, or stopped.
    \item Consequential action: any action that changes something outside the system: sending, submitting, purchasing, posting, or creating, editing, or deleting an email or event. Reading, navigating, searching, and drafting are not consequential.
    \item Approval: the user's explicit consent to one consequential action with its specific details, used once and void if any detail changes.
    \item Barge-in: the user speaking while the system is speaking; it stops the speech only.
    \item Stop request: an explicit ``stop working'' command (spoken or by key) to end a task's execution.
    \item Stop acknowledged / stop confirmed: the system has received a stop request / has verified that no further actions will run.
    \item Verified outcome: a result checked against the real account or page state. Unknown outcome: a consequential action whose result cannot be determined.
\end{itemize}

Technical terms: LiveKit, Hermes, Browser Use, MCP (Model Context Protocol), OAuth, VoiceOver, STT (speech-to-text), TTS (text-to-speech), LLM (large language model), POC (proof of concept).

\nsection{G.1 Context and overall objective}

Many websites and applications communicate information, choices, and state changes visually. Blind users can face barriers completing multi-step digital tasks and knowing whether those tasks succeeded. Natural Control is a voice interface that lets a blind user delegate tasks in a web browser and in Gmail and Google Calendar to an AI agent, while staying informed and in control.

\nsection{G.2 Current situation}

Today, blind users complete these tasks with screen readers such as VoiceOver, navigating each interface element by element, or with help from a sighted person. Existing AI computer-use agents assume the user can watch the screen to monitor and correct them.

\comment{Add findings from the CNIB interview (Aaron) and any participant conversations: which tasks people get stuck on, which tools they use, and where those tools break down.}

\nsection{G.3 Expected benefits}

\begin{itemize}
    \item Delegate, don't navigate: the user states an outcome (``reply to Alex'') instead of navigating the interface step by step. (G1)
    \item Control without sight: the user can understand, approve, correct, and stop the agent without seeing the screen. (G2, G4)
    \item Trustworthy results: results are checked against the real account or page before being reported, so the user does not need sighted help to confirm what happened. (G3)
\end{itemize}

\comment{Support each benefit with evidence (interview findings, prior research).}

\nsection{G.4 Functionality overview}

The user starts a session from the web client and speaks a task. The system clarifies missing details, carries out read-only steps on its own, asks for approval before every consequential action, reports progress and verified results by voice, and accepts corrections and stop requests at any time. A task history records what happened.

\nsection{G.5 High-level usage scenarios}

\begin{itemize}
    \item Reply to an email.
    \item Add an event found on a webpage to the calendar.
    \item Compare information on an unfamiliar website.
    \item Correct or stop a running task.
    \item Reconnect after a dropped connection without duplicating an action.
\end{itemize}

\comment{Draw a use case or activity diagram for these scenarios.}

\nsection{G.6 Limitations and exclusions}

\begin{itemize}
    \item Native Mac application control and general local-file tasks.
    \item Platforms other than Mac with Chrome; languages other than English.
    \item Phone calling and saved workflows (stretch goals).
    \item Fully local model inference; the system uses cloud AI and speech providers.
\end{itemize}

\nsection{G.7 Stakeholders and requirements sources}

\begin{itemize}
    \item Primary: blind and visually impaired people who want to complete digital tasks without visual feedback. Initial evaluation: blind Mac users with screen-reader experience.
    \item Secondary: other people who want nonvisual interaction.
    \item Setup helper: a person who completes the assisted setup.
    \item Requirements sources: the Problem Statement, Development Plan, and Hazard Analysis; TA and instructor guidance; prior research (WebAIM survey, Morae); the planned CNIB interview and participant sessions.
\end{itemize}

\comment{Record the CNIB interview date once done.}

\nsection{G.8 User profiles}

\begin{itemize}
    \item Experienced screen-reader user: fluent with VoiceOver or JAWS and keyboard navigation; wants speed on multi-step tasks and keeps their screen reader for everything else. Primary evaluation group.
    \item Less experienced or recently blind user: limited screen-reader skill; benefits most from delegation and clear spoken confirmation.
    \item Sighted user wanting nonvisual interaction: can see the screen but prefers or needs voice (busy hands, away from the screen); can verify visually, so has lower risk.
    \item Setup helper: comfortable with computers; connects accounts and grants permissions once, then is not needed for daily use.
\end{itemize}

\subsection*{S.2.1 Voice interface}
\addcontentsline{toc}{subsection}{S.2.1 Voice interface}

\begin{itemize}
    \item FR1: The system shall accept spoken input during a session. (G1)
    \item FR2: When the user speaks while the system is speaking (barge-in), the system shall stop speaking; the task continues unless the input changes or cancels it. (G2)
    \item FR3: On a bare ``stop'', the system shall stop speaking, pause new actions, and ask whether to cancel the task. A stop request (``stop working'' or the stop key) shall cancel the task. (G2; FR.Sa.1, FR.Sa.4)
\end{itemize}

\subsection*{S.2.2 Task bridge}
\addcontentsline{toc}{subsection}{S.2.2 Task bridge}

\begin{itemize}
    \item FR4: When required details are missing or ambiguous, the system shall ask instead of guessing, and recheck relevant information before resuming. (G3; FR.Sa.9)
    \item FR5: After IDLE\_PROMPT\_TIME without speech while a question is pending or a task is running, the system shall give one prompt or status update, waiting while the user is speaking. (G2; FR.Sa.11)
    \item FR6: The system shall accept corrections during a task without requiring a restart. (G4)
    \item FR7: On disconnection, the system shall pause new actions unless background work was authorized. On reconnection, it shall report the task state, reconcile uncertain outcomes, and wait for the user to continue. (G2, G4; FR.Sa.7)
    \item FR8: After a stop request, the system shall run no further consequential actions for the task, and shall report ``stopping'' and ``stopped'' separately, along with any actions that completed or are uncertain. (G2; FR.Sa.5)
\end{itemize}

\subsection*{S.2.3 Action gate}
\addcontentsline{toc}{subsection}{S.2.3 Action gate}

\begin{itemize}
    \item FR9: Every action not classified as read-only shall require approval of its exact details. Approval is an explicit affirmative answer to the pending approval question; silence or uncertainty is not approval. Changed details require new approval. (G2, G3; FR.Sa.3, FR.Sa.13, FR.Sa.14)
    \item FR10: Read-only information gathering and preparation shall proceed without approval. A failed read-only lookup may be retried once before it is reported as a blocker. (G1)
    \item FR11: The system shall never repeat an approved action, and shall check the real account state before retrying an action whose outcome is unknown. (G3; FR.Sa.6, FR.Sa.18)
    \item FR12: The system shall report each result as verified, partial, failed, or unknown, based on checking the real state. (G3; FR.Sa.10)
\end{itemize}

\nsection{S.4 Normal operation}

The user opens the web client and starts a session. They speak a task; the voice interface transcribes it and hands it to the task bridge, which starts it in Hermes. Hermes gathers information with read-only tools while the system gives spoken progress updates. When a consequential action is ready, the action gate holds it and the user hears its details read back; after an explicit approval the action runs, its result is verified, and the user hears the verified outcome. The task history records each step.

\nsection{S.5 Undesired event handling}

\begin{itemize}
    \item Misheard or ambiguous request: the system asks instead of guessing; read-back before approval catches remaining errors. (H2-a, H4-a)
    \item Stop not recognized or not effective: stop key as backup; no consequential actions after a stop request. (H2-b, H3-a)
    \item Disconnection: new actions pause; on reconnect, state is reported and nothing is repeated. (H3-b)
    \item Provider outage or timeout: the task pauses and the user hears what was and was not done. (H4-d)
    \item Unknown outcome: the real account state is checked before any retry. (H7-b)
    \item Instructions injected by a webpage or email: treated as data and reported to the user. (H6-b)
\end{itemize}

\nsection{S.6 Detailed usage scenarios}

Email reply: The user says ``Reply to Alex Chen's invitation and say Friday at 2 works for me.'' The agent finds the invitation and reads back ``Send Alex Chen: Thanks for the invitation, Friday at 2 works for me?'' The user says ``Yes, send it'', and the agent sends, verifies, and reports ``Your reply was sent to Alex Chen.'' The history records request, approval, action, and outcome.

Unfamiliar website: The user asks to compare standard and student tickets on a conference site. The agent navigates with general browser tools, reports prices and what each includes, says which details it could not verify, and incorporates the correction ``compare only tickets that include workshops.'' Nothing is purchased.

Ambiguous request: The user says ``Reply to Alex and say I can attend'' and two Alexes have sent invitations. The agent asks which one, waits, gives one reminder after IDLE\_PROMPT\_TIME, then proceeds with read-back and approval after the user answers.

\nsection{S.9 Formalization: task state machine}

A task is in exactly one state $q \in Q$, where $Q = \{$Working, AwaitingClarification, AwaitingApproval, Executing, Paused, Stopping, Stopped, Done, Failed$\}$. Events from $\Sigma$ move it by the partial transition function $\delta : Q \times \Sigma \to Q$ in Table~\ref{tab:fsm}. Active states: Working, AwaitingClarification, AwaitingApproval, Executing, Paused. Final states (Stopped, Done, Failed) are absorbing.

\begin{table}[H]
\centering
\caption{Task state transitions}\label{tab:fsm}
\begin{tabularx}{\textwidth}{lXl}
\toprule
\textbf{From} & \textbf{Event} & \textbf{To}\\
\midrule
Working & details missing or ambiguous, or a bare ``stop'' & AwaitingClarification\\
AwaitingClarification & user answers & Working\\
Working & agent proposes a consequential action & AwaitingApproval\\
AwaitingApproval & approve (explicit yes) & Executing\\
AwaitingApproval & reject, change, or expiry (user told it did not happen) & Working\\
Executing & result verified as ok, failed, or unknown & Working\\
Working & task verified complete & Done\\
Working & unrecoverable error & Failed\\
Any active state & stop request & Stopping\\
Stopping & in-flight work settled & Stopped\\
Any active state & disconnect (pending approval withdrawn) & Paused\\
Paused & reconnect and user continues & Working\\
\bottomrule
\end{tabularx}
\end{table}

Required properties:

\begin{itemize}
    \item P1: Executing is reachable only from AwaitingApproval through approve. Every consequential action therefore has an approval.
    \item P2: Leaving AwaitingApproval consumes the approval, so an approval is used at most once.
    \item P3: From every active state, a stop request leads to Stopping and then Stopped.
    \item P4: No transition leaves a final state.
\end{itemize}
