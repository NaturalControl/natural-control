\section{Demo Plans}

The main feasibility risk for the POC is whether a user can control a 
running general-purpose agent through voice alone. The speech and agent 
components exist separately, but it has not yet been shown that they work 
together. We have split this risk into two questions.

The first question is whether the system can receive instructions. The user's
speech has to be captured, turned into text and passed to the agent, and the
agent has to work out what the user wants from it. For a calendar request, that
means getting the right details, such as the title, date and time of the entry.
If any step loses or changes part of the request, the agent will do the wrong
thing even if the rest of the system works.

The second question is whether the system can control the computer. Once the
agent knows what the user wants, it has to carry out the steps needed to do it,
and then give the user a spoken summary of what it did. Because the user cannot 
see the screen, this summary is how they find out whether the task succeeded, 
so it has to be accurate and clear. The demo is meant to show both parts working together on one task.

For the demo, we plan to give spoken instructions to create an entry in Google
Calendar and then delete it. This is intentionally a simplified version of what
the final system will do, since the goal of the POC is only to demonstrate that
the approach is feasible. More complex tasks will be developed and tested after
the POC.

\section{CICD via GitHub Actions}

The repository uses one GitHub Actions workflow,
\href{https://github.com/NaturalControl/natural-control/blob/main/.github/workflows/latex-pages.yml}{\texttt{latex-pages.yml}},
to build and publish the documentation. It runs on every pull request to main,
on every push to main, and on demand, whenever a change touches the documents,
the references, the Makefile or the build scripts. It works out which documents
the change affects and rebuilds only those, using the repository's Makefile.

On a pull request, the workflow checks that the affected documents compile, so a
broken document is caught before it is merged; the Development Plan requires
these checks to pass before anything is merged into the protected main branch.
On a push to main, it also commits the rebuilt PDFs to the \texttt{pdfs/} folder
for TA review and deploys them to the project's
\href{https://naturalcontrol.github.io/natural-control/}{GitHub Pages site}.

We have started devloping the POC and are experimenting with its CICD workflows. 
The plan is to have workflows for the linting, code formatting, and automatic tests.
These will be moved into this repository when applicable.

\section{Team Charter Trigger Items}

\textbf{Trigger summary.} The team charter (Development Plan, Appendix C) and
the Development Plan's meeting and communication plans set these measurable
expectations:
\begin{itemize}
\item Two unexplained missed commitments in one month trigger a private recovery
conversation, and the TA is involved if the problem remains unresolved.
\item Drafts are ready 48 hours before a deadline.
\item Each meeting's agenda is posted as a GitHub issue at least 24 hours in
advance, and attendance and decisions are recorded on GitHub.
\item Actionable Discord messages receive a reply within one working day.
\end{itemize}

\textbf{Observed trigger events.} The events are summarized for the team as a
whole.
\begin{itemize}
\item Drafts of each deliverable existed before its deadline, but most editing
and merging happened on the day before or the day of the deadline. This period
overlapped with midterms in other courses.
\item Some team meetings were not recorded as GitHub issues, and the comprehensive agendas
were often posted on the meeting day rather
than 24 hours ahead. While agendas were often not given in advance,
the team did keep personal meeting notes.


\end{itemize}

\textbf{Plan and Reflection.} Although trigger events were reached, the team collectively
agreed that no corrective actions were necessary. 
The team will open a draft pull request at least 48 hours before
each deadline, so that the final day is for review rather than writing. The
meeting chair will post each agenda as a GitHub issue the day before the
meeting, and attendance and decisions will be recorded on that issue. The
triggers themselves remain appropriate and are not being revised.
